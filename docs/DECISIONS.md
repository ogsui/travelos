- 2026-10-24 · Sessions instead of JWTs · opaque 256-bit tokens, SHA-256-hashed at rest in `sessions`, sent as an HttpOnly cookie (and as a Bearer token for API clients) with a server-side TTL and instant revocation · a stolen database cannot be replayed as a login, logout really invalidates, and no signing key has to be rotated; opaque tokens need one indexed lookup per request, which is negligible at agency scale · short-lived JWT + refresh-token rotation, stateless signed cookies · engineering
- 2026-10-24 · CSRF for cookie auth · double-submit token: a readable `travelos_csrf` cookie must equal the `X-CSRF-Token` header on unsafe methods; Bearer requests are exempt · protects the dashboard without a server-side CSRF store, while API clients that never send cookies are unaffected · SameSite-only protection (insufficient on older browsers), per-session CSRF column · engineering
- 2026-10-24 · MFA policy · TOTP is required for `owner` and `admin` at login; an owner/admin without a secret gets `403 mfa_enrollment_required`; rotating an existing secret requires a currently valid code; enrollment itself requires the password. Agents/accountants may enroll but are not forced to · the two highest-privilege roles can change kill switches, users and autonomy, so a password alone must not be enough; requiring a valid code to rotate stops a stolen password from replacing the second factor · optional MFA for everyone, WebAuthn (later), email OTP (weaker and needs a channel) · engineering
- 2026-10-24 · TOTP implemented locally · RFC 6238, SHA-1, 6 digits, 30-second period, ±1 period drift, verified with `hmac.compare_digest`; tested against the RFC vectors · the verification path is ~40 lines, has no supply-chain or native-dependency surface, and is easy to review; standard authenticator apps interoperate · `pyotp` (small but unnecessary dependency) · engineering
- 2026-10-24 · Kill-switch precedence · deployment environment switch (`KILL_SWITCHES__<NAME>`, default OFF) is the operator hard gate; the `feature_flags` row is the owner's audited switch. Effective = operator gate AND owner value, with no row meaning OFF; an operator OFF can never be overridden from the API · outbound capability needs both a deliberate deployment decision and an audited owner decision, so one compromised owner session cannot open a channel the operator has not enabled · DB-only flags (no deployment gate), env-only flags (no runtime control or audit) · engineering
- 2026-10-24 · Cached feature flags · in-process per-`(tenant,key,scope)` cache with a 30-second TTL; writes invalidate locally, other workers converge within the TTL · avoids a database read on every outbound-capability check without adding Redis to the safety path; a 30-second window is acceptable because disabling a channel is not a sub-second emergency and the operator switch is instant · no cache (simpler, more load), Redis pub/sub invalidation (extra dependency and failure mode) · engineering
- 2026-10-24 · Workflow definitions as immutable data — six machines live in `workflow/definitions.py`; `StateMachine.fire` is pure and returns the target plus effect-event names. The transition service does not store state; the domain table owns its `state` column and writes it in the same transaction as the audit row and outbox events — one tested engine for every workflow, no second source of truth, and effects cannot commit without the state change. Alternatives: a workflow-instance table (duplicate state), hard-coded per-entity transition methods (six copies to drift) — engineering
- 2026-10-24 · Outbox delivery contract — producers write `outbox_events` inside their transaction; a dispatcher claims with `FOR UPDATE SKIP LOCKED`, retries with jittered exponential backoff and dead-letters to `human_tasks` after 5 attempts. Every handler runs in a nested transaction and claims `idempotency_keys(key=event id, scope=outbox)` before its side effect — at-least-once delivery never becomes double-apply after a crash or redelivery, and an unhandled event is visible as a human task instead of being dropped. Alternatives: exactly-once broker semantics (not available across PostgreSQL + Redis), in-memory retries (lost on crash) — engineering
- 2026-10-24 · Persistent timers — one `workflow_timers` row per `(tenant, name, subject)`, re-armed by upsert; firing is one-shot under `FOR UPDATE SKIP LOCKED`, sets `fired_at`, and writes `timer.fired` + audit in the same transaction. Unique-per-subject stops reminder storms after retries; re-arm covers changed due dates and repeat cadences. Alternative: a timer row per schedule (duplicates after redelivery), Celery ETA tasks only (lost on broker restart) — engineering
- 2026-10-24 · Campaign `resume` edge — `PAUSED -> RUNNING` is added beyond the documented `RUNNING -> PAUSED | COMPLETED` chain so an operator can recover a paused campaign without editing rows by hand. It is the only extra edge; owner should confirm or remove it when campaign operations are specified (task 026) — engineering
- 2026-10-24 – Approval catalogue as code – `approval/matrix.py` is the authoritative ceiling for every action: default, maximum, LOCKED, owner-only and four-eyes. Owner rows in `autonomy_policies` may lower autonomy but are clamped to the ceiling, and LOCKED rows are forced to their fixed default even if the database is tampered with – a config file, API caller or seed cannot turn a LOCKED action automatic, and the resolver fails closed on unknown actions. Alternatives: DB-only policy rows (a bad seed can unlock money actions), config-file ceilings (deploy-time and easy to drift from the document) – engineering
- 2026-10-24 – Approval lifecycle in one table – `approval_requests` keeps proposed, final, context, one or two reviewers and timestamps; status is pending/approved/edited/rejected/expired. A1 always opens a request, A2/A3 act automatically (A2 marks review-after), A0 denies without writing. Auto actions still write an audit row and event so "the machine decided" is visible. Alternatives: separate approval and decision tables (more joins, no simpler invariant), no request for A0 (silently loses the attempt) – engineering
- 2026-10-24 – Four-eyes is a downgrade, not a flag – when the catalogue, owner flag or value threshold requires two reviewers, an automatic decision becomes `needs_approval`. The first approval leaves the request pending; a second, distinct reviewer completes it, and the requester can never decide their own request. A machine cannot replace two humans. Threshold `0` disables the value trigger until the owner sets real amounts – engineering
- 2026-10-24 – Escalation and expiry as persistent timers – every request schedules `approval.escalation` then `approval.expiry`; both write owner human tasks and outbox events. The worker has one `timer.fired` handler that routes approval names and raises for any other name, so unrelated timer events still dead-letter rather than disappearing. Defaults 30 min / 24 h are safety timings pending owner confirmation – engineering
- 2026-10-24 – Idempotent policy seed – `admin/seed.py` inserts missing catalogue rows, repairs any row above its ceiling (and any LOCKED row that differs from its default), and preserves a safer owner-lowered level. Re-running changes nothing. This makes bootstrap safe on every deploy and also repairs a tampered database without overwriting legitimate caution – engineering
- 2026-10-24 – Automatic demotion only; promotion stays human – a daily beat task demotes one level when incidents > 0 in 30 days or the approved-unchanged rate over at least 50 proposals is below 85%, with an idempotency claim per metric window so a repeated job cannot cascade. LOCKED actions are never demoted, and promotions remain an explicit owner change through the audited endpoint. The matrix's promotion criteria are recorded but not automated – engineering
- 2026-10-24 – LLM provider policy enforced before the call – a provider advertises `no_training` and `synthetic_only`; a prompt declares its data class. Only synthetic data may reach a training-allowed or synthetic-only provider; customer/public data needs `no_training=True` and `synthetic_only=False`. An ineligible call is recorded and escalated without a network request – a policy check that fails closed is cheaper than trusting every caller to pick the right provider, and the data class travels with the versioned prompt rather than a call-site argument – alternatives: per-call policy flags (easy to forget), provider-side filtering (too late, data already left) – engineering
- 2026-10-24 – Reversible placeholders for prompt PII – detected emails, phones, cards, Aadhaar, passport numbers and explicitly `sensitive` variables become `[[TYPE_N]]` placeholders; the mapping lives only in process memory for one call and is restored in the model's answer. Stored requests, responses and logs keep placeholders – logs need redaction to be irreversible, but a useful draft sometimes needs the real name back; keeping the mapping out of the database and out of audit rows separates the two – alternatives: irreversible redaction everywhere (drafts lose names), encrypting the mapping in the row (more key handling and retention risk) – engineering
- 2026-10-24 – JSON Schema subset instead of Pydantic for LLM output – the prompt registry points at a JSON Schema file; a small validator supports type/properties/required/additionalProperties/items/enum/const/length/range/anyOf/oneOf/allOf/$ref. Unknown keywords are ignored, as JSON Schema specifies. Prompt schemas are data, not Python classes, so a prompt change does not require a code deploy, and the validator has no `Any` fallback – alternatives: Pydantic models per prompt (safe but code-coupled), a full `jsonschema` dependency (larger surface, unnecessary for the used subset) – engineering
- 2026-10-24 – One repair, then a human – a schema-invalid response gets exactly one repair request that includes the validation errors and the schema; a second failure falls through to the next provider, and total failure writes a high-priority owner task. The gateway never loops on a model that cannot follow the schema, and cost/latency stay bounded – alternatives: unlimited repair (runaway cost), no repair (avoidable escalations) – engineering
- 2026-10-24 – `llm_calls` is append-only – every provider attempt, repair and blocked call is a row, protected by ORM listeners and PostgreSQL UPDATE/DELETE/TRUNCATE triggers; the shared trigger function now reports the table name. Cost and latency history is evidence for budgets and incident review, so it must not be editable in place – alternatives: mutable usage counters (no audit trail), logs only (no queryable cost) – engineering
- 2026-10-24 – Development cache only – successful schema-valid responses are cached in-process with a short TTL, keyed by tenant, prompt/version, data class and the redacted request; the factory disables the cache in live mode. It exists to keep tests and evals cheap, not to serve production traffic – alternatives: Redis cache (another failure mode in the safety path), no cache (slow, costly local loops) – engineering
- 2026-10-24 – Zero budget means free-only, not no-cap – `ProviderPricing.free` is an explicit flag with zero rates; a budget of `0` filters the chain to free providers and blocks with a human task if none is eligible. Unpriced paid providers default to `free=False`, so "we have not set a price yet" cannot silently spend money. Only OpenCode model IDs ending in `-free` are marked free – alternatives: treating every zero rate as free (an unpriced paid model would run unmetered), blocking every call at zero (makes the owner's free-model policy unusable) – engineering
- 2026-10-24 – Budget day follows the business timezone – spend resets at midnight in `LLM_ACCOUNTING_TIMEZONE` (Asia/Kolkata by default), not UTC, so the owner's daily allowance matches the agency's working day – alternatives: UTC (resets at 05:30 IST), a fixed offset (breaks if the business timezone changes) – engineering
- 2026-10-24 – Retention purge is the one controlled append-only exception – the owner set 90 days for redacted `llm_calls`. A transaction-scoped PostgreSQL flag lets the trigger accept DELETE only from `LLMCallRetentionService`, which clears it immediately and writes an audit row with counts and the cutoff; UPDATE and TRUNCATE remain blocked. It guards against accidents and ad-hoc SQL, not a compromised app process; a dedicated database role would be the next step if that threat matters – alternatives: keep rows forever (violates data minimisation), allow unrestricted deletes (loses cost evidence), move to cold storage (no requirement yet) – engineering

- 2026-10-26 · Requirement required-field policy · Required fields per trip type live in deterministic code (`inquiry/rules.py`), not in the parser prompt: flight needs origin/destinations/start date/adults; package/hotel/group also need rooms; hotel needs checkout; visa needs nationality. Budget is recommended but never blocking because quotes are tiered, and an ambiguous field is reported as a gap even when a value is present. A field the parser asserts without a source span raises `SilentAssumptionError`; neutral defaults (`infants=0`, `urgency=normal`, `INR`) are not assertions. Alternatives: make the LLM decide what is missing (untestable, can be talked out of it), make budget blocking (would stall quotes without a budget) · engineering
- 2026-10-26 · Parser evidence as verbatim quotes, spans computed in code · The model returns 1-3 exact quotes per filled field; the parser locates them in the original message and stores character spans (`SourceSpan`). This keeps offsets correct even though the gateway redacts PII before the provider sees the text (placeholder substitution changes string length), and a reviewer can verify a quote directly. Missing evidence raises `SilentAssumptionError`; a quote absent from the message raises `RequirementParseError`. Neither is auto-repaired: a model that invented support cannot be trusted to fix its own evidence, so 010c turns the failure into a human task. Alternatives: ask the model for character offsets (unreliable and wrong after redaction), store no evidence (fails INQ-3 and the zero-silent-assumption gate) · engineering
- 2026-10-26 · Inquiry persistence and the NEEDS_INFO loop · Requirement versions are append-only rows (`requirements`), enforced by ORM `before_update`/`before_delete` listeners that raise `AppendOnlyError`; a database trigger is deferred so a future tenant-purge job can remove rows through one controlled path. Each version stores the prompt name/version, provider, model and `llm_call_id`, so eval results stay attributable. A blocking gap parks the inquiry in `NEEDS_INFO` and `assert_ready_for_search` fails closed; no supplier search is wired. Clarifying questions are deterministic templates submitted as `message.clarifying_questions` (A1 by default) and stored in an encrypted `message_drafts` row; there is no sender, so approval never produces an outbound message. Duplicate detection is explainable (`same_conversation`, `same_customer`, `same_contact_fingerprint` within 30 days) and only opens `inquiry.duplicate_suspected`; it never merges customers. Alternatives: let the LLM generate the question text (unreviewable wording and possible price/legal claims), auto-merge on a contact match (irreversible without approval), write a draft as an outbound message row (would look sent) · engineering
- 2026-10-26 · Inquiry eval modes and gold discipline · Gold is hand-written from the message (`data/eval/inquiry_gold.jsonl`) and every asserted value carries a verbatim quote checked by code; the synthetic generator's gold is never used because it was drawn independently of the message. The runner has `fake` and `provider` modes: `fake` echoes gold through the real schema/evidence/scoring path so CI proves the plumbing but labels the result `not_measured`; `provider` calls the owner-configured gateway and is the only mode that can pass the 95% accuracy, zero-silent-assumption, zero-parse-failure and full-injection-containment gate. A fake run refuses to overwrite a provider result, and a missing result file for a prompt version is a failure, not a pass. Precision/recall are field-level over required fields (a wrong value is both a false negative and a false positive); extraction accuracy is over every asserted gold field so preferences and budgets are not silently ignored. Alternatives: gate on fake mode (would fabricate a passing number), reuse the synthetic gold (contradicts messages), let a missing result count as success (hides unevaluated prompts) · engineering
- 2026-10-26 · Sales drafts use reviewed templates plus a deterministic claim guard · Acknowledgements use a `conversation` template only when the owner has reviewed the exact wording (`owner_approved=True`); the shipped placeholder is unapproved, so the service refuses it rather than inventing brand voice. Free-form replies are accepted only after `conversation.guard` finds every price, availability, policy, discount and hard-promise claim backed by a right-kind source ref (`quote:`, `inventory:`, `kb:`); a wrong-kind source does not count. Drafts go to `message_drafts` with `kind`/`template_key`, an encrypted body, and an A1 approval (`message.instant_ack` or `message.sales_reply`). The body is deliberately absent from `approval_requests.proposed`; only guard kinds and source refs are in the approval context. No LLM, no sender. Alternatives: let an LLM write the acknowledgement (invents tone and unsupported promises), store the body in the approval payload (unencrypted customer text), treat any source as covering any claim (a quote would "support" a visa rule) · engineering
- 2026-10-27 · Handoff triggers and summaries are deterministic, not model-written · Anger, complaint, every booking value (the owner chose that, not a threshold), customer-stated budget, legal, visa and refund/cancellation language, plus repeated identical questions, are detected by plain code in `conversation/triggers.py`. A hit creates one `human_tasks` row (`conversation.handoff`) plus a `conversation_handoffs` row holding the reason codes and an encrypted summary built from structured rows (`conversation/summary.py`). The queue in the dashboard is the only destination; no sender exists, so a handoff cannot message anyone. The detector deliberately over-blocks: a false positive costs a human glance, a false negative can leave a complaint, refund or legal threat unanswered. Repeated calls while a task is open refresh the same task and merge new reasons instead of duplicating it; complaints and refunds still hand off from a closed inquiry because they usually arrive after the sale. Loop threshold (3 exact repeats in 7 days), priority, assignee role and the summary field list are placeholders until the owner supplies the taxonomy, SLA and required fields. Alternatives: let an LLM decide when to escalate (unreviewable, can be argued out of it), one new task per message (queue spam), put the summary in the unencrypted task title (leaks customer text) · engineering
- 2026-10-27 · Sales-reply rubric scores fixtures with the real guard, and admits what it cannot measure · Task 011c adds a deterministic eval over hand-labelled candidate replies (`data/eval/sales_replies.jsonl`) and compromised replies (`data/eval/sales_injection.jsonl`). Every case is scored by the production claim guard and handoff triggers, so a guard regression that lets an unsourced price, availability, policy, discount or promise through fails CI with `unsupported_promise_rate > 0`. The rubric names five dimensions but only claims three as measured: `no_unsupported_promise` and `sourced_only` are deterministic; `accurate` is partial because claim detection is tested while source truth belongs to the quote/inventory/KB tasks; `helpful` and `on_brand` are `not_measured` because no model or owner brand-voice samples exist. Fixture source refs must use `quote:`, `inventory:` or `kb:`. Customer injection text is treated as data: a clean reply passes, a compromised reply is blocked, and a refund/visa request hidden in an instruction still hands off. The eval also exposed guard gaps for Hinglish `rupaye`, `lakh`/`crore` and `45k`, which are now covered. Alternatives: score invented replies with a fake mode that always passes (dishonest), gate on helpful/on-brand from an LLM judge (not implemented, and would invent the owner's taste), leave the eval until task 018 (no protection for the guard in the meantime) · engineering
- 2026-10-27 · Normalized supplier port and a deterministic in-memory simulator · Task 012a1 adds `SupplierAdapter` (search, price, rules, hold, book, cancel, retrieve, wallet_balance), frozen Pydantic `Offer`/`FareRules`/`CancellationRules`/`Hold`/`Booking`/`CancellationResult`/`WalletBalance` models with integer paise and UTC timestamps, a fixture `SupplierSimulator`, and an adapter-agnostic contract suite. A search may carry several legs; a failed leg becomes a `SearchFailure` so the caller gets partial results with `complete=False` instead of an empty answer. The simulator is in-memory and not thread-safe: holds, bookings and scenario activation live per process, and persistence, immutable snapshots, parallel search, circuit breaking and audit records move to 012a2. `book`/`cancel` exist on the port only for the future booking orchestrator (task 020); no API or service in this slice can reach them, the adapter has no approval logic and it never moves money. - 2026-10-27 · Supplier searches fail soft, and price snapshots are append-only · Task 012a2 adds `suppliers`, `supplier_searches` and `price_snapshots`, a `SnapshotStore`, a parallel `SupplierSearchService` and a per-supplier circuit breaker. Each adapter runs on its own worker with a per-supplier deadline; a timeout, open circuit or typed adapter error becomes a `SearchFailure` per requested leg while other suppliers still return offers, so the outcome carries `complete=False` instead of pretending a partial answer is full. A successful result is written as one immutable row per offer, and a later price is a later row. Immutability is enforced twice: ORM `before_update`/`before_delete` listeners raise `AppendOnlyError`, and a PostgreSQL trigger reuses `travelos_block_append_only` so raw SQL cannot rewrite history either. The same normalized query hash plus an unexpired batch is reused as a cache, with `expires_at` capped by the snapshot TTL so a long supplier validity window cannot keep a stale price live. The circuit breaker is in-process and per supplier: opening only affects that worker, and a restart clears it. The orchestration timeout abandons a worker thread rather than killing it, so portal adapters must still enforce their own page/socket deadline. No API, worker or booking path is wired: `book`/`cancel` remain unreachable until the booking orchestrator (task 020) and approval engine exist. Why: the rest of TravelOS needs stable, attributable prices and must keep working when one authorized portal is blocked or slow. Alternatives: let one failure abort the whole search (needless loss of usable prices), update a snapshot in place (destroys quote provenance), cache by inquiry/customer (mixes customer data into the price key), keep the breaker in Redis now (no operational need before multiple search workers) · engineering
- 2026-10-27 · Packages are assembled deterministically, with policy-driven occupancy and templated explanations · Task 013a adds the pure `packages` domain: `TravellerParty`, `RoomPlan`/`RoomAllocation`, `Itinerary`/`ItineraryDay`/`ItineraryComponent`, `BuildProblem`/`PackageBuild`, an `OccupancyPolicy`, `assess_occupancy` and `build_package`. Every chosen component carries a machine-readable `SelectionReason` and a templated explanation naming the supplier, offer, exact price and candidate count; no LLM is involved. There is no database, pricing, tax, tier or booking behaviour in this slice; persistence, the three option tiers and the gold component baseline are task 013b. Why: the rest of TravelOS needs a reviewable itinerary whose choices can be explained without a model, before any quote is priced or persisted. Alternatives: let an LLM pick components (untestable and can be argued out of the rules), include every component type by default (adds cost the customer did not ask for), rank on preference tags now (the normalized offers carry no star/board/attribute data), persist and tier in the same slice (well over the review budget) · engineering
